# wg-review

Resolve `WORKGRAPH_ROOT` by resolving symlinks on this installed `SKILL.md`, then taking `../..` from its containing skill directory (the directory containing `conventions.md` and `vendor/`), never from the target repository or current working directory. Paths below use that resolved root; it is not a host-provided environment variable.

Read `${WORKGRAPH_ROOT}/conventions.md` first. A final PR to `develop` is not reviewed here (conventions PR review and merge): stop and report it for human review. You are the loop driver. You never edit the PR's code and never merge. Under `wg`, the coordinator does step 2, spawns the reviewers and drives the loop; a setup subagent does step 1 and the worktrees and installs of step 3 and returns the intent and worktree paths; a lead-judge subagent does steps 4–5 (see "Lead judge"); invoked directly, you do all of them.

## Each round

1. **Scope.** Pin the PR head SHA. Read the Linear issue (acceptance criteria, Test design, Estimate), the Architecture slice if any, the PR body and its evidence. State the intent in one paragraph, as in step 2 of `${WORKGRAPH_ROOT}/vendor/cursor-plugins/pstack/skills/interrogate/SKILL.md`.
2. **Roster.** `n = min(estimate, 2)`. Assign models and focuses for this round with the conventions roster rule, including the pre-review credit. The author model is the PR body's `Author-model:` line; the round is one more than the latest `wg:review` marker's (below), or 1.
3. **Spawn** all reviewers at once, each in its own detached worktree at the pinned SHA (`git worktree add --detach <tmp>/wg-rv-<ISSUE-ID>-<r>-<i> <SHA>`, conventions agent labels). A fresh worktree has no dependencies: install them with the repo's frozen-lockfile command before spawning, holding the check lane. If that is impossible, say so in the prompt and have the reviewer cite the implementer's run output for those checks, marked `not rerun`. Build every prompt from the template in `${WORKGRAPH_ROOT}/vendor/cursor-plugins/pstack/skills/interrogate/references/reviewer-prompt.md`, filled with:
   - the intent, the diff (`gh pr diff`), the issue text, the PR evidence;
   - `references/rubric.md` and `references/code-quality-review.md` from the same interrogate folder;
   - the reviewer's assigned focus from conventions;
   - the high-signal filter and false-positive list from `${WORKGRAPH_ROOT}/vendor/claude-code/plugins/code-review/commands/code-review.md` steps 4 and "Use this list…" (only flag what you can show; no pre-existing issues, no linter-level nits);
   - the evidence rule: "each finding = file:line, reproduction you actually ran, observed vs expected output. You may run tests and the app inside your worktree. Cite the recorded verification runs for this SHA instead of rerunning them; run focused reproductions. Unreproduced suspicions go under `Unverified`."
   - for a native subagent, the conventions waiting rule: "run long commands (mutation runs, suites, CLI calls) in the foreground and wait inside that call, or in repeated foreground wait loops under the shell timeout; never `run_in_background` or `Monitor`, and end your turn only when the findings are written";
   - the output rule: for a native subagent, "write your full findings to `<tmp>/review-<r>-<i>.md` and reply only with that path and a count line (Act-on candidates / Unverified)"; for a CLI reviewer, "end with your full findings as your final message" (conventions: the CLI saves it to that path);
   - for round ≥ 2: the previous round's findings and the implementer's replies; "check each claimed fix by rerunning its reproduction, then review the new diff". Give the delta diff (`git diff <previous SHA>..<SHA>`) in place of the full PR diff, plus the PR's changed-file list; the reviewer reads the rest from its worktree (`git diff <base>...HEAD`).
4. **Synthesize and judge** per interrogate steps 4–5 and `references/lead-judgment.md`: merge duplicates, note which models raised each, bucket into Act on / Consider / Noted / Dismissed. A finding without a reproduction cannot be `Act on`. If you doubt one, validate it with one extra subagent on the other model, per code-review step 5.
5. **Post.** One `gh pr review` per round. Its body starts with the marker `<!-- wg:review wg=<version> sha=<SHA> round=<r> verdict=pass|changes author=<A> reviewers=<claude count>/<codex count> act=<n> consider=<n> dismissed=<n> unverified=<n> solo=<claude-only>/<codex-only> -->` (bucket counts from step 4; `solo` counts Act-on and Consider findings raised by only one model), and each Act-on finding carried from an earlier round is labeled `attempt <k>` (the number of fix pushes it has survived). Later stages and resumed sessions read state from the latest marker, not from the wording: `--request-changes` with the Act-on findings as inline comments (each with its reproduction), or `--comment` when nothing is Act on. Put the nonblocking Consider items in the review body; carry their links into the final PR for the human reviewer. GitHub refuses `--request-changes` on a PR opened by the same account; then post `--comment` whose body starts with `**Changes requested (round <r>)**` and carries the same findings.

## Lead judge

Under `wg`, spawn one lead-judge subagent per round once every reviewer has replied. Its assignment: the intent, the pinned SHA, the reviewer output paths with each reviewer's model and focus, the previous round's review URL, and steps 4–5 above. It may spawn no subagents, so it validates a doubted finding by rerunning the reproduction in its own worktree at the pinned SHA, or through the other model's CLI as a leaf assignment (conventions CLI assignments). The judge runs on the host family, which may be the author's: before it puts a finding raised only by `B` under `Dismissed` or `Noted`, `B` must confirm that call through its CLI with the finding and the judge's reason; if `B` disagrees, the finding goes to `Consider`. It reports in the conventions handoff format: the verdict (pass, or the number of Act-on findings), the posted review URL, and the Act-on findings as the text to forward to the implementer.

## Loop

- Act-on findings → send them to the implementer (`wg-implement` "During review"). When it pushes, start round r+1 with the new head SHA. The roster flips.
- Round passes when it yields zero Act-on findings and every earlier Act-on item has rerun evidence that it is fixed. For an intermediate PR to `project/<slug>`, comment "Review passed at <SHA>: ready for coordinator merge" (under a `verdict=pass` marker) and report the PR URL, base branch, reviewed SHA and evidence to `wg`; no human review is required for this PR. When invoked directly on an intermediate PR, hand off to `wg` for the merge rather than asking the user to merge.
- After a `needs-human` stop that ends in a redesign, restart at round 1: the roster and focus rotation reset and the redesigned diff counts as new code. Earlier Act-on findings carry over only as reproductions to rerun.
- Stop and add `needs-human` (with a comment saying why) when round 3 still yields Act-on findings, the same finding survives 2 fix attempts (its `attempt` label), reviewers and implementer disagree with evidence on both sides, or a fix needs an `interface` change.

**Override check.** After reading the upstream files and before acting on them, reread this file's overrides. Where upstream and these overrides or `conventions.md` differ, the overrides win; skip the upstream parts they replace instead of reconciling them.
